# InnerJAPI Lua 开发

先读项目根目录 `AGENTS.md` 和 `docs/Lua开发规则.md`，再读取所改模块的实际实现。规则中的实验结论只适用于记录的引擎版本；没有证据时保留不确定性。

- 为每个新入口注明同步玩法或本地显示域，确定资源所有者及取消/销毁方式。UI 发命令，收到同步消息后校验再执行业务；函数名带 ac/sync 不构成同步保证。
- 保持稳定业务 ID 与本端 handle/frame 分离。不要把枚举顺序、时钟、GC、弱表、地址和本地 UI 状态引入同步决策。
- 延迟回调校验对象仍有效。取消任务立即解除捕获引用；结束 scope 时注销事件并释放自有资源。不要让 GC 决定原生游戏对象销毁顺序。
- 性能改动先确定调用频率和测量边界。分别记录 Lua 分配/GC、任务/原生调用成本；不套用“闭包总比表贵”等固定排序，不以多开争用下的 FPS 宣称单客户端收益。
- 使用项目调度器；业务层新增原生 timer/trigger 或切换 handle_level 前，说明现有能力不能满足的理由并补相应实验。不要直接导入上游 ac、同步解码器或默认热更入口。
- 普通 Lua 改动运行 `python tools/check.py`；涉及原生/UI/同步时按项目独立测试入口验证。多人运行使用本机 `war3-runtime-test` 技能和 `D:/War3/tools/LanTest/README.md`，不使用桌面自动化。
- 根据真实失败完善规则和回归用例。记录构建标识、版本、数据、场景和未覆盖项；不要只增加禁止条款或把个例写成通用性能定律。
- 新原生探针先核对运行器的完成协议：实际断言成功后输出 PASS 和 UT_DONE。不能只打印完成标记，也不能为通过检查改写原始日志。源码变动后，以新的构建 ID 重新确定最终验收集合。
- 新标准库用法先确认内嵌支持；宿主 Lua 可用不等于游戏可用（本轮发现 os.remove 缺失）。运行时写入的临时文件按项目/玩家隔离；UI 裁剪同时审查鼠标、滚轮和快捷键输入。热更仅更新 view，不能通过本地文件更新同步玩法。

项目 skill 随模板复制。新增原生特性、热更新或性能结论时，先查询对应研究报告和测试证据；旧基线不是新代码的验证结果。

固定依赖项目先检查 framework.lock.json，公共模块在 deps 下，业务不能用同名模块覆盖。升级应显式更新内容锁并运行回归。地图构建保留源地图自己的初始化与单次 Lua 引导；按固定 w3x2lni 的 LNI 分类放资源，检查实际报告与最终 MPQ，不能只看退出码。

单位相关工作先读《单位生命周期与handle复用》。优先使用 game.unit.service 管理事件桥、所有权与停止路径；不要把原生状态轮询当成即时删除通知或完整事件历史。动态变身技能同时验证永久保留、最终类型、ID 与 epoch。真实 handle 复用采用全端固定分批，原生数值只供诊断。测试入口必须拒绝未完成构建或地图哈希变化，失败构建产生的文件不算可测试产物。

业务开发同时读《正式业务目录与技能样板》。复用 game.skill 的施法所有权，地图公式留在 rules。新增技能明确校验、准备、提交和中断语义；准备失败清理已分配资源，原生伤害重入死亡后再次检查施法有效性。禁止重复开始等被拒绝命令产生恢复或奖励副作用；旧会话请求不能操作新会话。

检查原生事件入口的异常路径、应用部分初始化失败和清理失败后继续释放；整应用重启与本地 view 热更是不同能力。业务相关改动用 gameplay 套件验证真实技能/挑战，而不是仅跑旧 UI 示例。资源结论包含固定重复工作量与空闲对照、Lua/原生分层指标和实际持续时间，不把 Windows句柄数当作 War3 handle 数。不继承模板历史 evidence 宣称派生项目已通过。

涉及请求/结果时检查seq匹配、队列满载、资源耗尽、迟到结果与本地超时；入队不等于成功，超时不触发同步退款或自动重试。涉及玩家退出时先撤销权限、后清理拥有资源，并注明借用和转移对象策略。本模板第二轮研究按《第二轮已确认目标》核对；派生项目按自己的目标和改动范围验收，不机械重做历史研究。原生分阶段资源矩阵与重复业务对照是不同证据，不用组合压力替代所有独立负载。
