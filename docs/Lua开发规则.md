# InnerJAPI Lua 开发规则

适用：本模板和派生项目，固定 InnerJAPI 1.49-9、Lua 5.3、handle_level 0。此文件随实验更新；最终证据见《扩展实机验证报告》，旧《实机验证报告》保留历史。新实验结论注明日期、构建及覆盖范围。

## 模块和调用域

核心基础层不依赖项目玩法。业务依赖公共 API，不依赖 UI 实例是否存在。模块尽量通过参数传依赖；require 不应隐式创建单位、timer 或 trigger。启动/停止接口和作用域由 app 统一负责。

同步域只使用所有客户端一致的输入、逻辑 tick、状态和确定性顺序。UI/鼠标/键盘/文件/网络/本地日志/实际时间属于本地域。边界通过命令桥传递经过约束的意图，接收时验证玩家身份、对象存活、控制权、资源和业务条件。命令入队成功不等于业务成功。

ac 是命名空间，不能自动同步。同步与本地调度 API 必须能区分，不能从本地回调直接安排玩法任务。上下文检查不是原生 API 沙箱；直接调用原生仍由开发者负责。

## ID、迭代和随机

handle/frame 是本机身份，可复用；稳定 entity ID 在全端一致的创建路径分配，删除后失效且单局不复用。先给对象建立确定性身份，再按身份排序；不能按 Group 枚举/未排序 pairs 的顺序分配 ID 或做顺序敏感操作。

玩法 RNG 的调用数、候选成员和候选顺序必须一致。随机选目标前按稳定 ID 排序，平局规则写清楚。日志探针不能额外抽样玩法 RNG。显示随机使用独立本地源，不能消耗玩法 RNG。

os.clock、os.time、墙钟、帧率、内存量、GC/弱表回收结果和对象地址不参与玩法条件、ID、随机种子或同步任务顺序。它们可以用于本地测量或显示，测量结果不能反过来改变本局玩法工作量。

## 所有权、闭包和资源

每个原生资源及长期事件/任务必须有所有者。明确谁创建、谁取消、何时销毁、销毁后引用如何失效。单位/组/计时器/触发器/frame 的原生生命周期不由 Lua GC 自动兜底。

匿名函数正常使用。关注的是捕获数据大小、注册次数、持有者和解除路径。取消任务应立即清空 callback 并脱离队列，不能等到原定超时时刻。保留取消 token 时也应释放捕获对象。销毁控件先取消任务、注销事件并处理子控件，再释放父资源。

异步/延迟回调使用稳定 ID 再解析存活实体，避免旧数字 handle 指向新对象。回调中取消自己、取消其他任务、销毁 owner 和重复清理应有明确语义。批量清理遇到一个错误仍要尝试释放其余资源，同时保留错误。

不要通过 __gc、弱表消失或本地 UI 分支销毁同步原生对象。ref/unref 要与实际持有责任配对，不能因“数字 handle 不 GC”忽略引擎引用规则。

## 调度、事件和错误

业务使用共享时钟上的 Lua 调度，避免每个技能/控件自行创建经典 timer。明确单位（tick/毫秒/秒）、最小间隔、同 tick 顺序、暂停、取消与异常策略。高频事件优先稳定入口和按需派发，而不是无限添加原生闭包入口。

事件注册返回注销句柄，owner 停止时注销；定义派发过程中增删监听器的行为。同步异常要输出可定位错误并停止危险的后续处理；本端 pcall 成功不代表业务一致，捕获错误不代表恢复了 OOS。

调度器先收集的到期列表只是候选；实际执行前必须重新检查任务仍存在、未暂停且仍到期。前一个回调可能取消、暂停或重新安排后一个任务。停止后的服务拒绝新注册时，检查必须发生在修改计数或持有回调之前。本轮终审为这两类边界补了失败复现和原生回归。

正式构建不加载任意代码字符串、作者本地路径、默认 F5 热更和定期全量 GC。开发热更必须限模块、可卸载、处理旧回调和状态，并在失败后恢复可用界面；同步玩法不会随本地文件修改自动更新。

本轮规则修订：调度器和事件默认 sync，local 调度器自动包裹本地上下文；文件热更探针最初在 local 域安排同步任务，被守卫正确拒绝，已改用 UI 任务。内嵌运行时没有 os.remove，不能假定桌面 Lua 的全部标准库存在。正式业务引入新标准库功能前先确认原生环境支持。

运行时写入的本地临时文件按项目和玩家隔离，尤其多开时的 FDF、开发探针文件和日志。开发者维护的只读 view.lua 可以按项目共享，因为它只更新本地显示。隐藏与裁剪不只影响绘图，输入命中、滚轮和快捷键也必须遵守相同区域规则。构造中途出错应释放已分配控件，不能只验证成功后的 destroy。

## 性能规则与测量

“每个函数便宜一点就一定提高 FPS”和“闭包 > 表 > 拼接 > 比较”的固定成本排序均不作为规则。先看热点调用次数、输入规模、分配字节、原生调用和整体瓶颈；再决定复用、批量、缓存或调度结构。

区分闭包创建与调用、空表与填充表、短/长字符串和不同拼接方式。分别测 GC 正常开启时的总成本，以及解释分配行为的受控实验；后者不用于宣传正常游戏收益。报告预热、迭代数、样本数、空循环基线、计时精度、是否含 GC、原生版本及并发客户端数。

高频循环避免不必要的临时表、字符串格式化、全表扫描和重复 native 属性读写。优化必须保留语义：缓存可能过期，对象池必须清理引用，排序/容器替换不能改变确定性顺序。不要仅因函数是匿名的就改写它。

原生 UI 成本与纯 Lua 微基准分别记录。任务规模、控件数量和采样间隔注明；内存平台期不证明没有原生泄漏。UI 更新可采用脏标记/合并更新，但不能让本地性能差异决定同步业务进度。

六客户端原生样本已经出现“填充表、唯一短串拼接比捕获闭包更贵”的结果；固定成本排序不能进入代码规范。参考《性能GC与时钟实验》的工作负载和原始样本，不直接比较不同迭代数的整行耗时。

## 验证与证据

修改后按影响面运行离线检查、打包回读、原生单测及多人实验。多人证据包含各端实际断言、状态摘要、房主 OOS 和清理记录，不能只看进程存在或未掉线。故意分叉控制用例应能触发检测。

未覆盖的视觉、输入、平台网络和长期资源行为明确记录；不把脚本 API 读回等同像素效果。实验发现按“事实/推测/待测”区分，规则随证据修订。
