# 原生性能、GC 与时钟实验

闭包、表、字符串不应按一个固定价格表选用。优化关注每秒实际工作量、分配量、原生调用和帧预算；降低一个极少执行的函数成本，可能没有可测的 FPS 变化。换成复杂缓存还可能扩大常驻内存或破坏同步语义。

## 实验方法

`src/probes/performance.lua` 在游戏内实际 Lua VM 执行，本地结果不参与玩法决策。每项先预热，再记录五次固定迭代样本；样本前显式收集垃圾，计时区间内保持正常 GC。原始 `[BENCH]` 记录保留总耗时和测量前后 Lua 堆差；这个差值不是总分配量，也不包括引擎/驱动的原生内存。

空循环是参考开销，未机械地从每项减去它。闭包样本每次捕获新的局部变量；不能拿可能被 Lua 复用的无捕获函数表达式来代表所有闭包。字符串比较样本使用已经存在的字符串，拼接样本含数字到字符串转换及生成不同内容，这两者是不同工作，不能只看“字符串”三个字。

事件样本为 100 个监听，重复 5,000 次 emit；任务样本包含创建 1,000 个长延迟任务、推进 1,000 tick、stop。原生 UI 样本重复修改同一个文字控件 20,000 次，不等于完整 UI 每帧渲染耗时。相同文字的去重/脏标记可另行测量，本模板没有用一个微基准推算全局 FPS。

另有两个有界分配实验暂时停止 GC，创建 10,000 个捕获闭包或空表，立即恢复 GC。它们用于解释分配量，不代表正常游戏应关闭 GC。

## 已记录的六客户端样本

构建 `research-six-03`，会话 `20261112-053050-4e2fdf`，同一台机器六开。下面是每端五次样本中位数的范围，计时单位毫秒。多开争用、窗口状态和渲染负担会影响墙钟成本，因此单客户端测量另列，不能把此表叫作单客户端性能基准。

| 操作 | 迭代数 | 六端中位数范围 ms |
| --- | ---: | ---: |
| 空循环 | 250,000 | 2–3 |
| 捕获局部变量的闭包 | 250,000 | 68–75 |
| 空表 | 250,000 | 39–47 |
| 四元素表 | 250,000 | 79–102 |
| 不同短字符串拼接（含数值转换） | 250,000 | 192–200 |
| 已有字符串比较（含数组索引） | 250,000 | 16–20 |
| 100 监听的事件派发 | 5,000 次 emit | 87–102 |
| 1,000 个空闲任务推进 | 1,000 tick，含创建/停止 | 114–137 |
| 原生文字更新 | 20,000 | 27–32 |

这个案例中“闭包 > 表 > 字符串拼接”不成立。空表比捕获闭包便宜，填充表却更贵；唯一短串拼接最慢，但它包含转换和分配。只能据此建议避免热点里无意义的格式化和对象分配，不能禁止匿名函数。

停止 GC 的 10,000 次探针测得：捕获闭包约 546.875 KiB，空表约 468.750 KiB。这是当前内嵌构建的具体布局，不要搬用宿主 64 位 Lua 的对象尺寸推算游戏内存。

`tools/analyze_runtime.py --session SESSION` 从原始日志生成 analysis.json，保留每个样本、各端统计、时钟和资源曲线。最终单客户端补测及长期资源结果见《扩展实机验证报告》对应会话，不用后来的数字覆盖这次历史测量。

## GC 到底负责什么

GC（Garbage Collection，垃圾回收）追踪 Lua 对象的可达性并回收不再可达的内存。一个闭包与 table 即使互相引用，只要外部没有任何可达入口，也可以被收集。反过来，只要事件表、任务队列或原生回调注册仍持有函数，它捕获的大对象就仍然活着。变量离开作用域不等于原生资源立即被销毁。

本模板取消任务、注销事件、销毁控件时解除引用；用弱表确认 payload 在保留 token 的情况下仍可回收。原生 timer 回调实验销毁八个计时器后，当前固定运行时的八个 payload 都可回收。它不能证明任何原生 API 的 callback 缓存都一定释放，也不能证明长时间 native frame 零泄漏。

单位/组/timer/trigger/frame 必须显式管理。GC 时间与弱表变化不一致，不能用于销毁同步资源、分配业务 ID 或决定随机调用。正式模式没有周期强制全量 collect；压力测试中的单端额外 GC 是故意制造客户端差异的测试条件，不是推荐生产设置。

## os.clock

Lua 文档将 os.clock 描述为程序 CPU 时间的近似值；它基于 C clock。Microsoft CRT 的 clock 则记录进程启动以来的墙钟时间，并明确指出这与 ISO C 的 CPU 时间语义不同。不能把文档概念直接当成当前平台的性能计数器。[Lua 手册](https://www.lua.org/manual/5.3/manual.html#pdf-os.clock)、[Microsoft clock](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/clock?view=msvc-170)。

原生探针把共享 500 tick（逻辑 5 秒）与 os.clock/os.time 一起记录。例如 UI 单端样本约为 6.561 秒与 7 秒，三端样本分别约 6.017、5.953、6.008 秒，而逻辑 tick 相同。此行为与本机墙钟风格实现一致；不是所有平台都如此，也没有因此证明底层唯一实现。

随后增加独立原生 5 秒 timer 对照（`research-clock-01`，会话 `20261112-063200-e59639`）：三端在原生 5/10/15 秒时都恰好记录 500/1,000/1,500 个共享 tick。P1 的 os.clock 则为 6.659/12.841/18.735 秒，P3 为 6.632/12.798/18.709 秒。因此这个场景中共享 tick 与原生游戏计时一致，墙钟更长不能直接解释为调度器自身漂移。不要用本地墙钟给同步 tick 做补偿；该短对照也不代替所有游戏速度、暂停和平台环境测试。

可以用 os.clock 做本地粗测、日志和显示动画节流，不能用它判断技能是否结束、分配同步任务顺序、设置随机种子或更新同步状态。本机样本分辨率约 1ms，因此 0–3ms 小样本的排序可信度有限；时钟还受实现范围和溢出限制。玩法用逻辑 tick；真实性能报告同时注明环境与测量方法。

## 调度器与优化取舍

当前调度器每 tick 扫描任务表，并按到期任务的创建 ID 排序。离线/原生探针验证了 1,000 空闲任务的成本，但这不是调度结构的规模上限。若实际项目有大量长期休眠任务，可进一步实验有序堆或时间桶；应保持取消立即释放、确定性到期顺序、暂停和错误语义后再替换。

优先降低真正的高频工作：合并同一控件的属性更新，数据变化时才重算文本，避免每帧格式化，复用稳定监听入口。不要为了少一个闭包而把所有状态塞进全局表，也不要以本机低 FPS 自动减少同步模拟步骤。局部性能调整不能改变全端玩法工作量。
