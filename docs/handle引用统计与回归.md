# handle 引用统计与回归

本次增量基于 `1bf9031`，固定 Warcraft 1.27 / InnerJAPI 1.49-9 / handle_level=0。只研究框架显式ref/unref的持有量与释放路径，不继续调查进程内存增长。先前37分钟长测属于原提交，不能作为本次新增源码的长测证据。

## 统计接口

```lua
local refs = require('scaffold.handle_refs').snapshot()
-- refs.active / refs.refs / refs.unrefs / refs.errors
-- refs.kinds.unit/effect/trigger/timer：各有 active、refs、unrefs、peak、errors
```

snapshot返回副本，不允许修改账本；不提供reset来掩盖残留。refs/unrefs是累计成功调用次数，active是当前持有的引用份数，peak是历史峰值。两次借用同一个单位可以产生两份引用，active不是独立对象数量。最后一次unref后移除对应数字handle诊断条目；复用这个原生编号时从零计数。

单位服务、原生战斗特效和共享桥接的ref/unref已统一接入。框架仍负责配对，业务只调用remove/detach/cancel/stop；不要为了统计再手动ref。普通Lua任务使用共享调度器，不能按任务数推导原生timer引用数。

无匹配unref在原生调用前拒绝。原生调用异常会记录errors并抛出，失败的unref不会把账面active减到零；实际原生副作用此时可能不确定，不能自动重试或宣称已经恢复。统计仅用于诊断和测试断言，不用于正式玩法分支；数字handle键不参与遍历排序或业务ID分配。

**范围限制：这是框架显式引用账本，不是引擎内部所有引用计数的读取。** 不包含JASS内部、插件内部、绕过适配层的原生调用或UI frame资源。游戏内测试确认真实API调用路径下的配对；离线测试另用独立模拟原生计数器交叉检查，不能将账本平衡扩大为引擎全局零泄漏保证。

## 回归设计

- 离线1000轮复用相同handle，每轮两份单位引用和一份特效引用，独立后端计数逐步对账；检查快照隔离、漏释放可见、无匹配释放拒绝、ref/unref失败保留错误及本地域禁止操作。
- 每端固定100批×20个真实单位；每批创建/移除后active回到批前基线，ref/unref各增加20。不依赖观察到的handle编号决定工作量。
- 每轮真实三英雄技能与挑战结束后，单位引用回到`3×玩家数+1`（英雄与借用对象），特效0、触发器2、共享计时器1，errors为0。失败准备、死亡、目标移除、复活、变身、控制权和模拟退出路径仍由gameplay套件执行。
- 应用stop后总active=0、累计refs=unrefs、errors=0；不依赖GC帮忙释放。每端业务状态摘要及引用轨迹由离线证据检查器比较。

本次增加的是统一统计、失配防护和回归；未因测试发现新的既有引用泄漏而修改业务生命周期。没有进行内存增长归因或新的30分钟长测。
