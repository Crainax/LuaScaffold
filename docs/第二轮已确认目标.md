# 已确认执行范围

来源：本对话用户确认的完整22项 /goal；按随后批注明确改为3英雄规模。此文件固定验收范围，不以已实现子集替代目标。

```text
/goal
在当前 LuaScaffold 已提交基线上，完善正式项目架构、固定版本依赖与 MainMap/UnitTestMap 的 w3x2lni 构建流程；研究单位生命周期和 handle 复用，实现完整 Lua 技能样板，并完成多人异常场景及资源增长对照。以固定版本源码、实际打包结果和游戏日志为准，将发现持续落实到框架、规则、skill 和回归测试，最后本地 Git 提交，不推送。

一、正式业务架构

1. 参考本地 MoeHero 的内容组织方式，明确以下层次：
   - scaffold：同步边界、稳定 ID、资源所有权、调度、事件及引擎桥接。
   - game：可复用的单位、技能与必要战斗机制。
   - app：具体地图的英雄、专属技能、天赋、副本、装备、规则、同步命令和界面。
   - ui：官方控件适配层；views：项目自己的界面。

2. 提供三英雄规模的目录说明，明确专属技能、专属天赋、公共效果、天赋系统、副本公共流程、具体副本/Boss、通用战斗流程和地图专属公式的归属。
   只实现本轮样板所需机制，不为填满目录创建大量空模块，也不提前扩展成完整 RPG 框架。

3. 明确共享定义与运行实例的区别：
   英雄定义、技能配置和副本定义可共享；冷却、天赋等级、任务、事件和副本会话状态必须由对应实例持有。
   内容按明确清单和确定顺序登记，不使用文件枚举或未排序 pairs 顺序分配业务 ID。
   require 默认只加载定义，不隐式创建同步原生资源。

二、脚手架固定版本依赖

4. 将“创建项目时复制的骨架”与“可升级的公共运行库”区分开。
   设计并落实固定 Git 提交或等效锁定机制，记录框架版本、InnerJAPI 载体哈希、工具版本及公共模块打包范围。
   不自动追踪最新分支，不让项目依赖开发机上随时变化的共享源码。

5. 提供独立示例项目验证依赖方式：
   项目业务不修改依赖内部文件；框架不反向依赖具体英雄或副本。
   构建将所需代码和载体完整打入地图，玩家运行时不访问开发机目录。
   验证固定版本重建，以及一次受控升级和回退；升级后运行对应回归。
   模板复制模式如保留，说明与固定依赖模式的边界及迁移方式。

三、MainMap/UnitTestMap 与 w3x2lni 构建

6. 建立正式地图 MainMap 和独立测试地图 UnitTestMap 的 LNI 源目录。
   参考 War3Lib 现有流程，保留必要的地形、地图信息、物编、资源、区域和预放置对象；不携带其测试业务。
   地图源目录保持可编辑，所有生成和注入操作在 build 的隔离工作目录进行。

7. 接入固定版本 w3x2lni：
   选择地图 → 建立构建工作目录 → 汇入项目 Lua、固定框架、载体和资源 → 生成/接入必要 JASS 引导 → 转换打包 → 校验最终地图。
   不提供 YDLua/InnerJAPI 切换选项，业务统一由 InnerJAPI Lua 执行。

8. 处理正式地图初始化与 Lua 引导的关系，避免用当前最小 war3map.j 覆盖区域、预放置对象等必要初始化，也避免重复启动 Lua。
   明确 LNI 物编字段、Lua 业务配置、rawcode 和资源路径的职责及引用方式。

9. 验证转换和优化不会遗漏 Lua 动态引用的物编与资源。
   对 w3x2lni 报告、引导、物编、模型/纹理/字体和 Lua 文件进行最终包校验。
   提供 MainMap/UnitTestMap 的编译、开发启动、测试、多人/OOS、压力及正式构建 tasks。
   正式包默认关闭并排除开发热更、实验探针和测试 harness。

四、单位生命周期与 handle 复用

10. 审查现有稳定 ID、实体登记、调度、事件和所有权实现，建立生命周期矩阵：
    创建、预放置登记、死亡、移除、复活、变身、召唤、所有者变化及业务对象失效。
    区分死亡与销毁，不预设变身等操作一定保留或更换原生身份，以实验确定支持语义。

11. 通过有界创建/销毁实验研究 handle 分配与复用。
    记录实际复用及触发条件；验证旧引用、旧事件和延迟任务不会误操作新对象。
    区分数字 handle、引擎引用和稳定业务 ID。
    未观察到复用时如实记录；可用可控模拟补充防护回归，但不得冒充原生复用证据。

12. 实现满足样板需要的最小单位对象层：
    确定性登记、稳定 ID 解析、明确状态、任务/事件所有权、幂等清理及失效后访问策略。
    为预放置单位建立可重复的身份方案，不按 handle 大小或未排序枚举顺序分配 ID。
    不通过 GC、弱表回收或本地 UI 回调销毁同步原生对象。

五、完整 Lua 技能样板

13. 制作可运行、可阅读的英雄技能样板：
    英雄生成或选择 → 发起施法 → 校验权限和资源 → 确定性选目标 → 延迟生效 → 伤害结算 → 冷却和本地 UI。
    增加一个影响该技能的英雄天赋，以及一个最小挑战场景，验证英雄、技能、天赋和副本目录的实际协作。

14. 覆盖目标提前死亡/移除/复活、施法者失效、取消、重复释放、多个玩家使用同一英雄定义等情况。
    业务使用共享调度和稳定 ID；UI 只提交意图，收到同步消息并通过校验后才修改玩法。
    明确技能、天赋和挑战会话结束时的资源清理责任。

六、多人异常场景

15. 扩展重复请求、过期 ID、无效或越权目标、权限变化、资源不足、队列积压，以及玩家退出时的处理。
    明确请求入队、请求接受、业务成功、拒绝和超时之间的区别。
    自动流程无法可靠覆盖的真实网络或退出场景，明确标注；模拟回归不冒充真实网络验证。

16. 完成单人及 3/6 客户端验证。
    制造不同本地 UI 状态、临时分配和 GC 负载，核对稳定 ID、单位状态、技能结果、资源消耗、冷却、天赋和挑战结果。
    运行故意 OOS 对照，确认房主检测链能够实际报警。
    不通过捕获错误后继续单端运行来掩盖分叉。

七、资源增长与性能对照

17. 设置空闲、单位生命周期、事件/任务、技能循环、UI 更新和组合负载的可重复对照。
    分别记录 Lua 堆、业务登记数、任务/事件/控件数、进程私有内存及 Windows 句柄。
    保持可比较的采样、GC、客户端数量和负载条件，不把 Windows 句柄数当成 Warcraft handleID 数量。

18. 对疑似持续增长进行重复与缩小范围实验，比较停止负载后的恢复。
    区分 Lua 引用未释放、正常缓存/分配器行为和尚未定位的原生增长；没有因果证据时不宣称修复。
    性能优化以实际热点为依据，不采用“闭包必然最贵”等固定排序。

19. 最终源码完成至少一轮 30 分钟的三客户端组合压力测试，包含技能、生命周期、挑战会话和差异 UI/GC 负载。
    如修复影响已验行为，重新建立对应构建和回归证据，不沿用旧源码成绩。

八、规则、交付与验收

20. 将实验发现落实为框架修复、回归用例、Lua 开发规则和项目 skill。
    保存失败探索、固定版本、构建参数、原始日志与证据等级；区分源码事实、原生实测、推测和未覆盖项。

21. 完成：
    - 离线语义与生命周期回归。
    - MainMap/UnitTestMap 实际 w3x2lni 构建和最终包回读。
    - 固定依赖版本、升级/回退及独立项目复制构建验收。
    - 单人、3/6 客户端、故意 OOS 和最终长压力验证。
    - 最终测试地图与交付 Lua 源码哈希核对。
    - 测试进程清理及全局启动隔离文件恢复确认。

22. 整理正式项目目录指南、依赖升级说明、地图/物编/资源构建指南、技能样板说明和研究报告。
    明确已实现 API、支持范围及人工验收边界。
    最后本地 Git 提交，不推送。

执行约束：
- 保留现有可验证基线；不修改上游快照和其他参考项目，不覆盖无关改动。
- 不使用 Windows 原生桌面自动化；游戏测试仅通过现有 CLI 和允许的自动入房流程。
- 同一游戏环境串行测试；保存日志，按记录的 PID/创建时间清理本次自动测试进程；人工启动的游戏保留。
- 必须有实际断言、完成标记及 OOS 证据；启动成功或没有掉线不算通过。
- 实验推翻现有假设时，先修正规则和设计，不为保留抽象而放宽验收。
- 对必须人工操作的视觉、输入或编辑器步骤提供简明说明，不虚报已经验证。
```
