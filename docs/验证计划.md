## 新业务的 OOS 检查方式

状态摘要按固定顺序纳入稳定 entity ID、类型/所有者、量化坐标、生命/资源、业务命令结果及实际 RNG 调用计数。不要纳入 handle、frame ID、table 地址、Lua 内存大小和墙钟；不要为了探针额外调用 RNG 改变序列。

单位枚举先转换成已登记实体并按稳定 ID 排序，再做顺序敏感逻辑。不能用枚举顺序给实体分配稳定 ID。同步对象的创建/销毁不能依赖局部 UI、GC 或弱表是否回收。

针对每项实际玩法，至少制造：不同 UI 状态、不同本地临时分配/GC、同类同位置候选对象、重复/过期/越权命令、实体销毁后延迟命令。比较每端业务结果，保留首个分叉之前的日志。基础模板没有业务权限知识，不能替项目决定购买、技能和存档规则。

## 自动测试约束

使用 LanTest CLI 和 war3-runtime-test 技能；不使用 Windows 原生桌面自动化、SendKeys、截图点击或旧 war3auto 回退。同一环境只跑一场，实际完成、失败或超时后保存日志，通过记录的 PID/创建时间调用清理任务并确认退出。用户人工启动的游戏不自动结束。

只有全部客户端有新日志、断言和完成标记，且房主无正常场景 OOS，才能判通过。故意 OOS 构建必须失败并有真实报警；启动进程或没有掉线都不等于通过。离线/编译检查也不代替实机验证。
